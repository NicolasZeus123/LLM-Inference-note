# 服务迭代预算、调度与异构协同

这篇按 容量状态 → 单轮预算 → 请求选择 → 动态批次 → 阶段调度 → 重叠与异构路由 的顺序整理四篇文章的内容。每一步都接着上一步留下的问题，同时又给下一步加上新的约束。

---

## 第 0 步：先建立全局图景——一个请求在推理服务里经历了什么

先把一个请求的完整流程铺开，后面的概念都挂在这条时间线上。

**阶段一：排队（Waiting）**。请求从网络进来，进入等待队列，此时还没占用任何 GPU 资源。

**阶段二：准入（Admitted）**。调度器确认系统有足够的显存格子给它，允许它进入活跃集合。这一步的关键是容量检查，也就是第 1 步要讲的容量状态。

**阶段三：Prefill（预填充）**。一次性把用户输入的整段 prompt 读进去，并行计算每个 token 的内部表示，生成 KV Cache。这一步是计算密集的，耗时短但会把算力吃满。

**阶段四：Decode（解码）**。基于 KV Cache 一个 token 一个 token 地往后生成。每步计算量很小，但每步都要把整个 KV Cache 从显存读一遍，属于内存密集。

**阶段五：完成（Finished）**。达到结束条件（EOS 或 token 上限），释放占用的 slot 和 KV 容量，请求离开系统。

KV Cache 在这里的作用是：模型生成每个新 token 时都要回头看前面所有 token 的 Key 和 Value，为了避免重算所以缓存下来。缓存越长，占的显存越多，这是后面所有容量问题的根源。

下面按顺序进入每一步。

---

## 第 1 步：容量状态——系统现在“还剩多少东西可以给”

这一步是整个调度决策的账本起点。调度器决定放谁进来之前，必须先知道现在还有什么。

### 1.1 三种被争用的资源

**KV Blocks（显存格子）**。显存被切成固定大小的 block，每个 block 装一段 KV Cache。请求根据 prompt 长度和要生成的 token 数声明自己需要多少 block，也就是 `required_blocks`。系统维护一个 `free_kv_blocks` 计数器，表示当前剩余的空闲 block。

可以类比成停车场：车位数量固定，每辆车按长度占若干个，`free_kv_blocks` 就是还剩几个空位。

**Slot（序列槽位）**。执行引擎能同时管理的活跃序列数量有硬上限。显存还剩很多，slot 用完新请求同样进不来。

**Token 预算（本轮可处理的 token 总数）**。每一轮前向能处理的 token 总量有上限，即 `max_num_batched_tokens`。这是按轮消耗的预算，不是持久占用的资源。

### 1.2 请求的状态机

调度器操作的不是一个请求，而是一个会变的状态对象。每个请求记录着自己的阶段、已生成长度、优先级、需要多少 block。

正常路径是线性的：`waiting → admitted → prefill → decode → finished`。

关键的分叉是 `preempted`（被抢占）。容量不够但来了一个更紧急的请求时，调度器可以暂停一个已准入且允许被抢占的请求，把它占的 block 释放出来。被抢占的请求进入 `preempted` 状态，保留自己的阶段和已生成的 token 数，等容量再次充足时从离开的地方继续。

这里有条不变量：一个已经 decode 了 50 个 token 的请求被抢占后恢复，必须从第 51 个 token 继续，不能从 0 重来，也不能重新 prefill。所有调度实现都必须守住这条线。

### 1.3 容量检查的逻辑

请求要进入执行，必须拿到足够的 KV block。准入规则是：

- 如果 `challenger.required_blocks <= free_kv_blocks`，直接扣减容量，准入。
- 不够的话看能不能抢占一个受害者。抢占的三个条件必须同时满足：
  1. 受害者是已准入但未完成的请求
  2. 受害者允许被抢占（`preemptible=True`）
  3. 受害者的有效优先级严格低于挑战者
- 找不到合格的受害者，或者释放一个之后容量仍然不够，挑战者继续等待。

只抢优先级更低的，是为了防止高优先级请求互相抢占导致系统抖动。只向下抢，优先级才构成单向的秩序。

这一步结束时，调度器知道了当前有多少 block、多少 slot、多少 token 预算可用，以及哪些请求可以被牺牲。这是下一步做预算的前提。

## 第 2 步：单轮预算——这一轮要花多久、最多能放多少

有容量账本之后要算两笔账：时间账（这一轮跑多久）和数量账（这一轮最多放多少请求）。

### 2.1 时间账：Roofline 直觉

单轮迭代时间可以近似写成：

> **T_iter ≈ max(T_memory, T_compute) + T_schedule + T_launch + T_exposed**

T_memory 是访存时间，即把数据从显存搬到计算单元的时间，由三件事决定：权重读取（模型参数读一次的成本，被本轮 token 数分摊）、历史 KV 读取（每个活跃请求的上下文都要读出来，上下文越长、活跃请求越多，读取量越大）、新 KV 写入（本轮产生的 KV 写回显存）。

T_compute 是计算时间，即矩阵运算的时间，取决于本轮 token 数和模型有多少参数真正参与计算（稠密模型全部参与，MoE 只激活一部分）。

取 max 的原因是 Roofline 模型的直觉：搬数据比算数慢时总时间由搬数据决定，属于访存受限；算数更慢时总时间由计算决定，属于计算受限。两者可以部分重叠，所以取较大值作为下界。

T_schedule、T_launch、T_exposed 是 max 消不掉的固定开销。调度器决策本身要花时间，向 GPU 提交任务和启动 kernel 要花时间，通信和同步如果没有被重叠隐藏就会暴露在关键路径上。

厨房再快，如果领位员决策慢、传菜路径长，顾客的等待时间还是会变长。

### 2.2 数量账：五类批次上界

批次大小不是可以随便拧大的旋钮，它同时被五个天花板压着，最终能放多少取最小值：

| 上界 | 约束什么 | 超过后先出什么问题 |
| --- | --- | --- |
| **Slot** | 最多同时管理多少活跃序列 | 无法补入新请求 |
| **KV 容量** | 每个请求的 KV 占多少显存 | 显存不足、被迫抢占或驱逐 |
| **Token 预算** | 本轮 Prefill chunk + Decode token 的总量 | 单轮时间拉长，TPOT 上升 |
| **SLO** | TTFT / TPOT / P95/P99 的延迟承诺 | 吞吐可能还在涨，但用户等待已经恶化 |
| **执行后端** | 计算内核、张量形状、运行时的硬性能力 | 收益饱和、回退甚至执行失败 |

最终可执行规模 = min(slot, KV, token, SLO, backend)，并且要记录是哪几个约束并列生效。并列的约束不能丢掉：如果五个上界恰好都等于 8，那五个都是 binding constraint。

### 2.3 什么是 SLO？

SLO（服务等级目标）是对延迟的硬性承诺，通常包含三项：

- **TTFT（Time To First Token）**：从请求到来到吐出第一个 token 的时间，主要受排队和 prefill 影响。
- **TPOT（Time Per Output Token）**：后续每个输出 token 的平均耗时，主要受 decode 阶段的单轮迭代时间影响。
- **P95/P99**：95% 或 99% 的请求必须满足的门槛，属于尾延迟指标，比平均值更能反映体验。

批次越大，一轮耗时越长，延迟越容易超过 SLO。所以 SLO 从延迟这一侧给批次大小设了上限。

### 2.4 什么是“运行拐点”（Operating Knee）？

这个量用来解释为什么批次不是越大越好。

增大 batch size 时，初期更多请求并行，硬件利用率上升，吞吐量快速增长；后期硬件逐渐跑满，吞吐增长越来越慢，但每轮迭代时间还在上升。

拐点算法是：按 batch 从小到大排序，逐个检查。

1. 如果当前 batch 的 `iteration_ms` 超过延迟门槛，停止，`stop_reason = 'slo_violation'`。
2. 计算相邻两档的吞吐相对增益：`(throughput_current - throughput_previous) / throughput_previous`。
3. 增益低于阈值（默认 10%）说明吞吐已经饱和，选上一档作为运行点，`stop_reason = 'throughput_saturation'`。
4. 一直既没饱和也没违反 SLO，就选最大的合法 batch。

拐点的含义是：再多放请求，吞吐几乎不涨，但延迟明显变差。越过这个点等于用延迟换几乎不存在的吞吐收益。

这一步结束时，调度器知道了这一轮最多能放 N 个请求、预计耗时 T。接下来是在 N 个名额里选哪些请求。

## 第 3 步：请求选择——名额有限时，先服务谁

有了容量和预算，调度器要从所有未完成的请求里选出这一轮推进谁，核心是排序规则。

### 3.1 排序键：一个共享的骨架

所有策略共用同一个排序键（schedule key），从左到右逐位比较，越靠前的字段决定性越强，键值越小越先被选中：

> **（deadline 松紧）→ 阶段 → 缓存命中 → 有效优先级 → 总长度 → 请求编号**

| 字段 | 含义 | 优先方向 |
| --- | --- | --- |
| **deadline 松紧** | 只在 Deadline 策略下启用，表示“离截止步还有多少余量” | 余量小者优先 |
| **阶段** | `prefill` 排在 `decode` 前面 | Prefill 优先 |
| **缓存命中** | 已有部分 KV 缓存的请求推进成本更低 | 命中者优先 |
| **有效优先级** | 业务优先级（Aging 策略下会被等待步数加成） | 数值大者优先 |
| **总长度** | 前面都相同时，短请求优先 | 短者优先 |
| **请求编号** | 最后的稳定 tie-breaker，防止排序抖动 | 小编号优先 |

业务优先级“越大越优先”在代码里靠取负号实现：优先级数值越大，取负后越小，排序键越小，排得越靠前。

### 3.2 三种策略

**Fixed Priority（固定优先级）** 完全按业务优先级排序。问题很明显，低优先级请求可能永远等不到机会，也就是饥饿（starvation）。`wait_steps` 在这里只做记录，不改变排序。

**Aging（老化）** 让等得越久的请求有效优先级越高：

> **有效优先级 = 业务优先级 + (等待步数 ÷ aging_interval)**

例如 `aging_interval=4`，初始优先级 1 的请求等了 12 步，有效优先级变成 `1 + 12//4 = 4`，可能反超初始优先级 3 的请求。`aging_interval` 越小老化越快，公平性越强，但高优先级请求也可能被拖慢。

**Deadline（截止步）** 面向有硬时间承诺的请求。每个请求带一个 `deadline_step`，调度器算完成余量：

> **余量 = deadline_step − 当前时钟 − 剩余所需步数**

余量越小越紧迫，排得越靠前。余量变成负数说明按当前速度已经来不及，标记 `deadline_missed`。

三者的分工是：Fixed 管谁重要谁先走，Aging 解决等太久的问题，Deadline 解决再不跑就超时的问题。Aging 和 Deadline 都是在 Fixed 的基础上加了一个时间维度的修正。

### 3.3 一轮 step 的完整逻辑

1. 收集候选：所有未完成的请求。
2. 按排序键排序：用当前策略算每个候选的排序键。
3. 依次尝试准入：从键值最小的开始调容量检查。够就直接准入，不够就尝试抢占，抢不到就跳过试下一个。
4. 第一个成功准入的成为 `chosen`，这一轮推进它。
5. 推进 `chosen`：`prefill` 阶段切到 `decode`；`decode` 阶段 `generated_len += 1`；达到 `max_new_tokens` 则完成并释放 KV block。
6. 没被选中的候选 `wait_steps += 1`，为下一轮 aging 积累。

这一步结束时，调度器只选出了一个请求。下一步要把这个选择扩展成“一轮批次里同时推进多个请求，并且每轮结束后重新组队”。

## 第 4 步：动态批次——每轮结束后重新组队

### 4.1 静态批处理的问题

假设三个请求：A 要生成 10 个 token，B 要 100 个，C 要 5 个。静态批处理下整个批次必须等最慢的 B 跑完 100 轮。从第 5 轮起 C 的位置空着，第 10 轮起 A 的位置也空着，GPU 座位被浪费，新请求又插不进来。

Anyscale 的基准测试里，生成长度差异变大时，静态批处理的吞吐从 200 tokens/s 掉到 81 tokens/s。

### 4.2 连续批处理：调度粒度下沉到“迭代”

连续批处理（continuous batching）的做法是：每一轮前向结束后做一次清点，已完成的请求移出批次并释放 slot 和 KV 容量，从等待队列补入新请求填满空出的位置。

这个“每轮结束时重新组队”的时间点叫迭代边界（iteration boundary）。它不改变模型的计算方式，只改变每轮批次里有哪些请求。

用前面的例子，第 5 轮 C 完成后离开，等待队列里的 D 立即补进 C 的位置。

### 4.3 补人不是“有空位就塞”：三重门槛

新请求必须同时通过三道门槛：

**第一道是 Slot**。执行引擎能同时管理的活跃序列数有上限，请求完成才空出 slot。

**第二道是 KV 容量**。每个活跃请求占一块 KV block，即使有空 slot，剩余 block 不够新请求也只能等。

**第三道是 Token 预算**。一个 decode 请求通常只推进 1 个 token，占 1 份预算；一个 prefill 请求可能一次处理一大段 prompt 或一个 chunk，占很多份预算。长 prefill 会挤压其他请求的准入空间。

关键原则是：三道门槛同时检查，按 slot → KV → token 的顺序返回第一个阻塞原因，不能跳过队首去接纳后面的请求。队首被卡住就保留队首等下一轮，保证公平性和可预测性。

### 4.4 四个状态与两个关键函数

| 状态 | 含义 | 本轮发生什么 |
| --- | --- | --- |
| **active** | 已在 batch 里，未完成 | 执行本轮分配到的 token |
| **finished** | 达到结束条件 | **退出 batch**，释放 slot 和 KV block |
| **waiting** | 在队列里，条件满足 | **转入 active** |
| **blocked** | 在队列里，有门槛没过 | **保留在队列**，下轮再试 |

`release_terminal_requests` 在每轮开始时清理 `finished` 的请求，把 KV block 归还到可用池。没有它，空出的容量不会被重新利用。

`iteration_token_demand` 决定一个请求这一轮吃多少预算：prefill 消耗 `min(剩余 Prefill token 数, prefill_chunk_size)`，decode 只要还有工作，最多推进 1 个 token。

### 4.5 推进一轮：阶段迁移

`advance_iteration` 在一轮执行完之后更新进度：

- 从当前阶段的剩余 token 数里扣掉本轮分配的量
- prefill 剩余归零时，phase 从 `prefill` 切成 `decode`
- decode 剩余归零时，status 变成 `completed`，在下个迭代边界被清理

阶段迁移是单向的：请求不会永远停在 prefill，也不会在 prefill 没做完就进 decode。这条状态链只能单向推进。

### 4.6 补满批次的代价

连续批处理天然倾向尽量补满 batch，因为并发越多吞吐越高。但补满是付代价的：

- **新请求的 TTFT 变差**：总是优先补满已有队列，新请求排到后面
- **长请求被饿死**：如果总是优先短请求（完成快、腾位置快），长请求可能永远排不上
- **尾延迟（P95/P99）恶化**：持续补满让每轮迭代时间变长，尾延迟首当其冲

需要监控的指标是 queue wait、batch occupancy、P95/P99 延迟和 starvation 计数。

这一步结束时，系统已经能边解码边换人了。但 prefill 和 decode 仍在同一个批次里互相干扰，一个长 prefill 会卡住所有 decode。下一步处理这个干扰。

## 第 5 步：阶段调度——Prefill 和 Decode 怎么分享同一轮预算

### 5.1 根本矛盾：两种“性格完全不同的工作”

prefill 是计算密集型：大量矩阵运算并行，耗时短但瞬间吃满算力，一次性申请大块 KV Cache，并发度低。

decode 是内存密集型：每步计算量小，但每步都要把整个 KV Cache 从显存读一遍，瓶颈在搬数据，并发度高。

prefill 要算力和瞬时显存，decode 要持续的显存带宽。硬塞进同一个批次，必然互相拖累。

### 5.2 Chunked Prefill（分块预填充）

很长的 prompt 如果一次性 prefill，会独占整轮的 token 预算和算力，让正在 decode 的请求全部卡住，产生明显的抖动（jitter）。

Chunked Prefill 把长 prompt 切成多个小块分多轮处理，与 decode 工作交错执行。`iteration_token_demand` 里 prefill 消耗 `min(剩余, prefill_chunk_size)` 体现的就是这个机制。

两者的分工是：continuous batching 管谁进谁出，chunked prefill 管一次吃多少。前者解决请求到达时间和生成长度不同的问题，后者解决单次长 prefill 阻塞其他请求的问题。

### 5.3 六层调度：从内到外的完整视野

调度可以拆成六层，每一层消费上一层的预算，做粒度更大的决策：

| 层次 | 决定什么 |
| --- | --- |
| **1. 请求选择** | 当前哪些请求获得执行机会（第 3 步） |
| **2. 准入与资源** | 新请求能不能进活跃集合（第 1 步） |
| **3. 迭代级组批** | 哪些请求进入下一轮实际批次（第 4 步） |
| **4. 阶段级调度** | Prefill 和 Decode 如何分享本轮 token 预算（Chunked Prefill） |
| **5. 执行级重叠** | CPU 准备、GPU 计算、状态搬运怎样在时间线上重叠（第 6 步） |
| **6. 实例池与异构路由** | 请求在哪个实例或 Prefill/Decode 池执行（第 6 步） |

前四层在一个执行单元内部做决策，第五层看时间线上有没有等待被暴露，第六层把粒度扩大到多个资源池之间。

### 5.4 PD 分离：把两种“性格”拆到不同池子

即使有 chunked prefill，prefill 和 decode 仍在同一个 GPU 池里争算力和显存带宽。PD 分离（prefill-decode disaggregation）的思路是把两者放到不同的 GPU 池上执行：prefill 池专做计算密集的预填充，decode 池专做内存密集的逐 token 生成。

好处是各用各的资源，互不干扰。代价是 prefill 算完的 KV Cache 必须从 prefill 池交接给 decode 池，这个跨池传输成为新的时间开销，甚至暴露在关键路径上，把分离的收益抵消掉。

这一步结束时，系统多了分池这个架构选项，但引出一个新问题：跨池交接的代价怎么算、等待有没有被隐藏。这就是最后一步。

---

## 第 6 步：重叠与异构路由——等待到底有没有被“藏起来”

### 6.1 状态交接的三种方式与“隐藏账单”

PD 分离之后，KV Cache 从 prefill 池传到 decode 池，有三种处理方式：

- **KV 交接（handoff）**：真正传输 KV Cache。传输量越大、链路越慢，`handoff_ms` 越高。
- **重算（recompute）**：不传输，让 decode 池重新计算 prefill 部分的 KV。省了传输，但浪费算力。
- **同池回退**：交接代价太高时，让请求回到同一个池完成 prefill 和 decode，放弃分离。

这里的原则是：`handoff` 和 `recompute` 的耗时不能重复计入，它们是对同一段工作的两种互斥处理方式。

### 6.2 执行关键路径：区分“总耗时”和“被隐藏的时间”

这一步最核心的是区分两种时间：

- **total elapsed（总耗时）**：请求真正等待的时间
- **overlap（被重叠隐藏的时间）**：被其他并行工作盖住的时间

CPU 准备、GPU 计算、数据搬运、KV 交接，如果串行排队，等待就暴露给请求，拉长端到端延迟；只有在依赖允许时让它们重叠，才可能真正缩短关键路径。

判断原则是：只有通信或搬运从关键路径上被移开，吞吐或尾延迟才可能改善。如果只是增加了并行任务，却引入同步、争用或池闲置，那不叫优化。

需要持续观察的证据字段包括 `queue_wait_ms`（排队等待）、`idle_gap`（GPU 空闲间隙）、`overlap_ratio`（重叠比例）、`handoff_ms`（交接耗时）、`exposed_comm_ms`（暴露的通信时间）、`cold_start`（冷启动是否混入热请求的性能）。

### 6.3 异构路由：两个池子“能力不同”时怎么送请求

异构 PD 路由处理的是更复杂的情况：prefill 池和 decode 池的硬件能力、链路带宽甚至执行后端都不一样。比如 prefill 池是算力更强的 GPU，decode 池是显存更大的 GPU，或者两池之间隔着慢网络。

这时路由决策不能只看谁有空，还要看状态交接的代价、池间负载是否平衡、要不要回退到同池。`handoff_ms`、`transfer_bytes`、`recompute_ms`、`P99` 和失败状态都是判断路由是否合理的证据。

### 6.4 五个容易混淆的对象

有五件事经常被当成一回事，实际不是：

| 对象 | 决定什么 |
| --- | --- |
| **请求调度** | 先服务谁、这一轮服务谁 |
| **缓存管理** | 请求的状态放在哪里、能保留多久 |
| **PD 分离** | Prefill 和 Decode 由哪个资源池执行 |
| **Attention–FFN 解耦（AFD）** | MoE 服务中注意力与 FFN/专家是否由不同进程组执行（引入双向激活传输和角色同步） |
| **异构路由** | 两池能力不同时，状态怎样交接、何时回到同池 |

它们可以协同，但改动一个不等于完成了其他：扩大缓存容量能提高可接纳并发，却不会自动改善队列公平性；把 prefill 和 decode 拆成两个池，也必须重新检查跨池通信和负载平衡。

### 6.5 接纳控制：系统扛不住时，选择“让谁等”还是“让谁走”

请求量超过资源能稳定处理的范围时，调度器还要做接纳决策。这不是简单拒绝，而是在几种动作里选：

- **排队**：资源短时不足但预计能恢复，保护请求完整性，代价是排队时间和 P99 上升
- **限流/拒绝**：队列或缓存超过安全水位，保护已接纳请求的 SLO
- **降级**：质量目标允许降低资源开销时，保护整体可用性
- **转移/扩容**：单池持续饱和时，保护服务容量

核心取舍是：接纳控制决定系统在负载上升时保持 P99，还是让所有请求一起变慢。

## 整条链条的回顾：六步如何串成一个闭环

把六步连起来，会看到一条从底层矛盾到架构拆分、每一步都给下一步制造新约束的链条：

> **第 1 步（容量状态）** 盘清家底：多少 KV block、多少 slot、哪些请求可被抢占。**第 2 步（单轮预算）** 算两笔账：这一轮要跑多久（Roofline + 固定税），最多放多少（五类上界取 min），拐点在哪里。**第 3 步（请求选择）** 在名额里排序选人：Fixed 只管优先级，Aging 解决饥饿，Deadline 解决超时；抢占只能向下抢，被抢占者保留进度。**第 4 步（动态批次）** 把“一次选一个”扩展成“每轮重新组队”：三重门槛同时检查、不跳过队首、Prefill 转 Decode、Decode 完成释放容量；补满批次有 TTFT、公平性和尾延迟的代价。**第 5 步（阶段调度）** 解决 Prefill 和 Decode 互相干扰：Chunked Prefill 把长 Prefill 切块交错执行，PD 分离把两种性格拆到不同池子，但引入交接账单。**第 6 步（重叠与异构路由）** 追问等待有没有被隐藏：只有通信或搬运从关键路径移开才算优化，handoff 和 recompute 不能重复计费，异构路由要看交接代价和负载平衡，接纳控制在过载时决定“让谁等、让谁走”。

每一步的概念都在前一步的账本上记账，每一步的产出都是下一步的输入。按这个框架去看任何一个具体的调度算法或架构选择，都能找到它对应在账本的哪个位置。
