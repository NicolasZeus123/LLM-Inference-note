# 1. KV 表示与容量：一个词元到底占多少显存

## 1.1 先理解 KV Cache 是什么

大模型是逐词元（token）生成回复的。为了在生成新 token 时记住前面的内容，模型会把历史每个 token 在注意力层里产生的 K（Key，键）和 V（Value，值）保存下来，这就是 KV Cache。

注意力里还有 Q（Query，查询），代表当前位置想找什么。注意力的核心计算是：

$$
\text{Attention}(Q,K,V)=\text{Softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V
$$

可以这样理解：Q 是需求，K 是每个位置的标签，V 是每个位置的内容，用 Q 和 K 匹配出权重，再对 V 加权求和。K 和 V 会被缓存，Q 通常不需要长期缓存，因为每个新 token 只产生自己的 Q。

## 1.2 多头、KV 头数：MHA / GQA / MQA / MLA

| 机制 | 核心做法 | 对 KV Cache 的影响 |
|---|---|---|
| **MHA（多头注意力）** | 每个 Q 头都有自己独立的 K 头和 V 头 | KV Cache 最大；KV 头数 $H_{kv}=H$ |
| **GQA（分组查询注意力）** | 多个 Q 头共享一组 K/V | KV Cache 按分组比例缩小；$1<H_{kv}<H$ |
| **MQA（多查询注意力）** | 所有 Q 头共享同一组 K/V | KV Cache 最小；$H_{kv}=1$ |
| **MLA（多头潜在注意力）** | 把 K/V 压缩成低维潜在向量，改变历史状态的表示形式 | 每个词元字节数减少，但仍然是缓存，仍要管理 |

几个概念要注意：

- 头数 $H$：Q 有多少个头。
- KV 头数 $H_{kv}$：K/V 有多少组。GQA 就是让多个 Q 头共享较少的 KV 头。
- 每头维度 $D$：每组 K/V 向量的宽度。

这里有个常见误解：以为用了 GQA、MQA、MLA 或者量化，就不需要分页、生命周期管理、前缀匹配了。不是这样。它们只改变每个词元存多少，不改变这些缓存怎么分配、共享、回收。

## 1.3 容量公式

近似公式：

$$
\text{KV 字节数} \approx 2 \times L \times H_{kv} \times D \times S \times B \times \text{bytes(dtype)}
$$

各变量的含义：

| 变量 | 含义 | 直观理解 |
|---|---|---|
| $L$ | 层数 | 每层 Transformer 都要存一份 K/V |
| $H_{kv}$ | KV 头数 | MHA 大，GQA 小，MQA 最小 |
| $D$ | 每头维度 | 每组 K/V 多宽 |
| $S$ | 上下文长度 | 已经积累了多少历史词元 |
| $B$ | 并发请求数 | 同时有多少请求在占缓存 |
| $\text{bytes(dtype)}$ | 每个元素字节数 | FP16 是 2 字节，量化后更小 |
| 系数 2 | K 和 V 各一份 | 所以乘 2 |

最重要的结论是：容量随层数、KV 头数、上下文长度、并发数近似线性增长。长上下文和高并发叠加时，显存压力上涨得非常快。

另外提一下尾块浪费：分页之后最后一个块可能没装满，但浪费被限制在一个块以内，比按最大长度预留的方案小得多。

## 1.4 本节小结

- KV Cache 存的是历史 K/V，作用是 decode 时不用重算历史。
- MHA/GQA/MQA 改变 KV 头数；MLA 改变表示形式；量化改变 dtype 字节数。
- 容量公式说明显存压力来自多个乘数，压缩表示不能替代管理机制。

# 2. 分页分配：PagedAttention 怎么把 KV Cache 散着存

## 2.1 连续预分配的问题

传统做法是每个请求按最大可能长度预留一整块连续显存。这带来两个问题：

| 问题 | 含义 | 后果 |
|---|---|---|
| **内部碎片** | 预留 8192 个位置，实际只用 50 个，剩下空着但不能给别人用 | 巨大浪费 |
| **外部碎片** | 请求结束后释放的连续块大小不一，七零八落 | 总空闲很多，但找不到足够大的连续块给新请求 |

用飞机座位的说法，就是给每个旅客锁死一整排，他只坐一个座位，别人也坐不了。飞机看着很空，很多人却上不去。

## 2.2 PagedAttention 的核心：固定块 + 块表

PagedAttention 借鉴操作系统虚拟内存分页的做法：

- **物理块（Physical Block）**：GPU 显存预先切成固定大小的格子，每块装固定数量 token，比如 16 个。
- **逻辑块（Logical Block）**：从请求视角看，它的 KV Cache 仍然是连续的第 1、2、3… 段。
- **块表（Block Table）**：记录逻辑块到物理块的映射。

关键是逻辑上连续、物理上不连续。请求的逻辑块 0、1、2 可以分别放在物理块 7、2、9，只要块表按顺序记下来，读取时按表拼接就行。

## 2.3 三个阶段的分配行为

| 阶段 | 发生什么 | 关键规则 |
|---|---|---|
| **Prefill（处理输入）** | 数 prompt 有多少 token，只申请需要的块数 | 不按最大长度多要 |
| **Decode（逐词元生成）** | 新 token 写入尾块 | **尾块没满不新增块**；只有跨过块边界才申请新块 |
| **Release（请求结束）** | 占用的块归还空闲池 | 块大小统一，归还后可立即复用，基本消除外部碎片 |

举个例子：块大小 16，prompt 20 个 token，申请 2 块（16 + 4）。decode 追加时尾块还有空位就不新增，填满并跨过边界才新增第 3 块。

## 2.4 与后续机制的分工

- PagedAttention 管物理显存怎么分页存。
- 前缀匹配和 Radix 管相同前缀怎么找回来复用。
- 生命周期管理管谁在用、何时回收、空间不够怎么办。

## 2.5 本节小结

分页分配用固定块加块表，把物理存储和逻辑连续解耦，几乎消除外部碎片，内部碎片最多压到一个尾块。它是后续共享和复用的物理基础。

# 3. 生命周期与容量控制：每块显存的“生死账本”

## 3.1 引用计数：共享的安全钥匙

多个请求可能共享相同前缀的 KV Cache。系统不复制物理块，而是让新请求引用已有块，并给缓存记录加引用计数 `ref_count`。

- 第一个请求创建时 `ref_count = 1`
- 第二个请求共享时 `ref_count = 2`，物理块不增加
- 请求结束时 `ref_count -= 1`
- 只有 `ref_count = 0` 才进入可回收候选

有一条硬规则：只要 `ref_count > 0`，说明还有活动请求在用，绝对不能驱逐或修改这些块。合租房间只要还有人住，房东就不能收回重装修。

## 3.2 五个生命周期事件

| 事件 | 何时发生 | 账本变化/规则 |
|---|---|---|
| **分配 Allocate** | 新请求 Prefill | 从空闲池取块；失败必须**干净回滚**，不能留半提交状态 |
| **追加 Append** | Decode 新 token | 尾块没满不新增；跨边界才新增块 |
| **共享 Share** | 另一个请求命中相同前缀 | `ref_count += 1`，物理块不变 |
| **释放引用 Release** | 请求结束/取消 | `ref_count -= 1`；归零后可能变 **reusable**，不一定立刻 free |
| **驱逐/回收 Evict/Reclaim** | 容量不足或主动清理 | 只能从 `ref_count = 0` 中选牺牲者；释放后空闲池增加 |

半提交状态要特别小心：分配 3 块成功、第 4 块失败时，前 3 块也必须干净退回，不能泄漏。

## 3.3 容量账本：不能只数“缓存条目”

| 状态量 | 含义 | 影响什么 |
|---|---|---|
| 有效 token 数 | 缓存覆盖多少 token | 判断尾块是否满 |
| 已占用 Block 数 | 实际占几个物理块 | 计算容量和新增分配 |
| 活动引用数 | 还有几个请求在用 | **>0 禁止驱逐** |
| 历史命中次数 | 前缀被复用几次 | 引用归零后判断值不值得留 |
| 最近访问时间 | 最后一次使用时间 | 区分冷热缓存 |
| **空闲 Block 数** | 总块数 − 已分配块数 | **真正决定能否接纳新请求** |

最容易误解的一点：请求结束后块可能从活动变成 reusable，仍然算在 allocated 里，不会自动变成 free。所以缓存条目不多，不等于空闲空间很大。

## 3.4 容量不足时的决策顺序

1. 先看空闲池够不够，够就直接分配。
2. 不够时只在 `ref_count = 0` 的缓存里驱逐，优先选：
   - 命中次数少
   - 最近访问时间早（冷）
   - 同等条件下占用块多
3. 冷缓存驱逐光了还不够，绝不能碰活动缓存，只能：
   - 排队，让新请求等
   - 抢占活动请求：换出到外部存储（省计算但有传输延迟），或者丢弃后重算（省传输但浪费计算、增加 TTFT）
   - 拒绝新请求

## 3.5 调度池 vs 缓存资源池

- 调度池：决定下一轮运行哪些请求，可以根据可用块数做准入和抢占决策。
- 缓存资源池：维护块的分配、引用、驻留、回收。
- 调度器不能绕过缓存状态机直接改引用计数。

## 3.6 本节小结

生命周期管理的核心是：引用计数保证共享安全；容量账本区分活动、reusable 和 free；驱逐只碰 `ref_count=0` 的块；活动引用永远受保护；每种容量动作都有代价。

# 4. 通用前缀匹配：相同开头怎么被识别和复用

## 4.1 Prefix Cache 在缓存什么

很多请求开头相同：系统提示词、多轮对话历史、长文档、few-shot 示例。相同前缀算出来的 KV Cache 也相同。Prefix Cache 把第一次算好的前缀缓存登记下来，后面的请求直接复用，跳过前缀的 prefill。

这里有个重要边界：Prefix Cache 主要加速 prefill，不加速 decode。它复用的是对输入的理解，不是对输出的生成。

## 4.2 什么才算可复用：精确因果前缀匹配

注意力是因果的，每个位置只依赖前面的 token。要安全复用，新请求的前缀必须和已缓存的前缀逐 token 完全一致，包括顺序、内容和边界。这叫精确因果前缀匹配（exact causal prefix match）。

中间偶然相同不算命中。缓存 `[1,2,3]`，新请求是 `[1,2,9,3]`，只有前 2 个连续命中，后面的 `[9,3]` 都算未命中后缀。

## 4.3 最长连续匹配与请求拆分

$$
H = \max_j \operatorname{lcp}(\text{prompt}, \text{cached\_path}_j)
$$

`H` 是从开头连续命中的最长长度。请求被拆成：

$$
\text{prompt} = \text{reusable\_prefix} + \text{suffix}
$$

| 量 | 含义 | 后续用途 |
|---|---|---|
| 命中长度 `H` | 从开头连续命中多少 token | 确定可复用范围 |
| 可复用前缀 | `prompt[:H]` | **跳过 Prefill** |
| 未命中后缀 | `prompt[H:]` | **仍然要 Prefill**，产生新状态 |
| 无命中 | `H=0` | 整个输入正常 Prefill |

拆分要满足一个不变量：命中前缀加未命中后缀，拼回去必须严格等于原 prompt。

## 4.4 复用账本

| 账本量 | 含义 | 结合什么看 |
|---|---|---|
| 命中词元数 | 可复用前缀长度 | KV 占用、TTFT |
| 未缓存词元数 | 仍需 Prefill 的后缀长度 | Prefill 耗时、吞吐 |
| 复用比例 | 命中词元数 ÷ 输入总词元数 | 命中率分布；空输入定义为 0.0 |
| 新增状态 | 后缀计算后写入的 KV Cache | 驱逐、迁移、生命周期 |

常见误解是觉得命中就等于完全不计算。实际只是把 prefill 从整段 prompt 缩小到未命中的后缀。

## 4.5 共享与驱逐

命中时不复制 KV Cache，而是让新请求引用已有块，`ref_count += 1`，物理块不增加。只要 `ref_count > 0`，块就不能被驱逐或修改。容量不足时，只能从 `ref_count = 0` 的冷缓存里按 LRU 或低复用价值驱逐；驱逐之后如果又被命中，需要重新 prefill。

## 4.6 本节小结

通用前缀匹配的逻辑链是：登记共享前缀 → 从开头做最长连续匹配 → 拆出可复用前缀和未命中后缀 → 用账本量化节省的 prefill → 通过引用计数安全共享 → 只驱逐 `ref_count=0` 的冷缓存。

# 5. Radix 索引：用压缩前缀树加速大量前缀的查找

## 5.1 为什么需要树

已登记前缀一多，新请求逐条比对就太慢了。RadixAttention 把这些前缀组织成基数树（radix tree），也就是压缩前缀树，新请求从根往下走一趟就能找到最长可复用路径。

## 5.2 压缩边是什么

普通前缀树每个节点存一个 token，长前缀会让树很深。基数树把连续的单 token 节点压成一条边，边上存一段 token 序列。

例如登记 `[0,1,2,3]` 和 `[0,1,2,3,4]`，压缩后是：

```
根 ──[0,1,2,3]──→ 节点A
                    └──[4]──→ 节点B
```

每个树节点的关键字段：

- `key_tokens`：这条边上的 token 序列
- `terminal`：是否有完整请求在这条路径末尾结束
- `kv_cache_ptr`：指向这段前缀对应的物理 KV Cache
- children：子节点

`terminal` 是安全复用的闸门。只有走到 `terminal=True` 且存在 `kv_cache_ptr` 的节点，才说明这段前缀对应真实的完整缓存。

## 5.3 三个操作

### 插入 Insert

从根出发，按子边首 token 找候选，计算新路径和子边的 LCP（最长公共前缀）：

- LCP 等于整条边，直接走过
- 还有剩余，新建子边
- 部分重叠，需要分裂

### 分裂 Split

已有边 `[0,1,2,3]`，插入 `[0,1,9]`，LCP 是 `[0,1]`，在 token `2` 处分叉。做法是：

```
原：根 ──[0,1,2,3]──→ 旧节点
后：根 ──[0,1]──→ 共享节点
                 ├──[2,3]──→ 旧节点（保留旧 terminal、children、kv_cache_ptr）
                 └──[9]──→ 新节点（terminal=True）
```

这里有个关键不变量：旧后缀必须原样继承旧边的 `children`、`terminal` 和 `kv_cache_ptr`，不能因为分裂把旧路径的身份弄丢。

### 匹配 Match

新请求从根出发逐段比较：

- 公共长度等于整条边，完全命中，继续往下
- 公共长度小于整条边，说明在边中间分叉，立即停止，不再深入
- 只有走到 `terminal=True` 的节点，才更新最长命中长度

为什么不能只看走了多深？因为树里可能有末尾没有完整缓存对象的半边，只看深度会把半截路径误判成可复用，读出来就是错的数据。

## 5.4 命中后执行计划

匹配得到 `H` 之后：

| 量 | 含义 | 动作 |
|---|---|---|
| 命中长度 `H` | 从开头连续命中多少 token | 读取对应前缀缓存 |
| 命中前缀 | `prompt[:H]` | 跳过 Prefill |
| 未命中后缀 | `prompt[H:]` | 执行剩余 Prefill，算完登记为新路径 |
| 完整路径标记与缓存引用 | `terminal=True` 且有 `kv_cache_ptr` | 确认命中可真正复用 |

这里同样要不变量：命中前缀加未命中后缀拼回去必须等于原 prompt。

## 5.5 与 PagedAttention 的分工

| | PagedAttention | RadixAttention |
|---|---|---|
| 管理对象 | 物理 Block | 词元前缀（逻辑路径） |
| 解决问题 | KV Cache 怎么分页存 | 公共前缀怎么快速检索复用 |
| 核心结构 | 块表 | 基数树 |
| 关系 | 提供物理存储基础 | 在存储之上提供前缀索引 |

PagedAttention 让 KV Cache 能散着存，RadixAttention 让相同前缀能顺着树找回来。

## 5.6 本节小结

Radix 索引用压缩边降低树深，用 `terminal` 保证只认可完整缓存路径，用 LCP 做插入、分裂和匹配。分裂必须保留旧后缀的身份；匹配遇到边中间分叉立即停止；只有终止节点才更新命中长度。

# 6. 真实复用验证：命中率不等于服务收益

## 6.1 为什么需要验证

前缀命中率高，不代表服务真的变快。可能命中的都是短前缀，省下的 prefill 很少；可能后端根本没真正报告缓存命中；也可能瓶颈在 decode、调度或显存带宽，而不是 prefill。

所以命中率本身不能证明收益，必须用 TTFT（首 token 延迟）和吞吐这类端到端指标来验证。

## 6.2 实验必须固定的变量

| 变量 | 为什么要固定 |
|---|---|
| 模型 | 不同模型容量和计算量不同 |
| 分词器 | 影响 token 数和前缀匹配 |
| 输入前缀 | 确保确实存在可复用前缀 |
| 输出长度 | 控制 Decode 工作量 |
| 并发度 | 影响显存压力和吞吐 |
| 采样参数/温度 | 影响输出和性能可比性 |

还要确认后端真的报告了缓存命中，而不是应用层自己以为命中了。

## 6.3 指标与对比

| 指标 | 看什么 |
|---|---|
| **TTFT** | 首 token 延迟，Prefill 复用的直接收益 |
| **吞吐** | 单位时间完成请求数/token 数 |
| **命中词元数/复用比例** | 命中了多少 Prefill 工作量 |
| **Prefill 耗时** | 是否真的下降 |
| **P50/P95 延迟** | 尾延迟是否改善 |
| **失败/拒绝/抢占次数** | 容量压力是否抵消收益 |
| **输出正确性/质量** | 复用不能改变结果 |

实验设计上有几点建议：先预热；多次重复；控制变量；对比“关闭前缀缓存”和“开启前缀缓存”；同时看平均延迟和尾延迟；在容量压力下观察驱逐和抢占有没有副作用。

## 6.4 常见误判

- 命中率高但都是短前缀，TTFT 改善小
- 命中率高但并发太高，显存压力导致抢占，吞吐反而下降
- 只测单请求，看不到并发和容量控制的影响
- 不验证输出一致性，可能复用了错误状态
- 不区分 prefill 和 decode 瓶颈，把 decode 瓶颈归因到前缀缓存

## 6.5 本节小结

真实复用验证要固定模型、分词器、输入前缀、输出长度和并发度，确认后端报告命中，比较 TTFT、吞吐、尾延迟和失败率，并验证输出正确性。命中率是过程指标，TTFT 和吞吐才是服务收益指标。

# 7. 按容量问题扩展：MLA 与 KV 量化

## 7.1 什么时候考虑 MLA / KV 量化

先判断容量瓶颈在哪：

| 瓶颈 | 优先手段 |
|---|---|
| 显存碎片、按最大长度预留浪费 | 分页分配 |
| 重复前缀导致重复 Prefill | 前缀匹配 + Radix |
| 活动/冷缓存混杂、空间不足 | 生命周期与容量控制 |
| **每个词元本身字节数太大** | **GQA/MQA、MLA、KV 量化** |
| 长上下文 + 高并发仍不够 | 组合使用上述手段 |

## 7.2 MLA：改变历史状态的表示

MLA 把 K/V 压缩到一个低维潜在向量里，改变的是每个词元存什么形式。它减少了每个词元的状态字节数，但仍然是缓存，仍然需要分页、生命周期管理和前缀复用。容量公式里不能简单套 $H_{kv}\times D$，要按压缩后的潜在状态字节数估算。

## 7.3 KV 量化：减少 dtype 字节数

KV 量化把 K/V 从 FP16 等格式压到更低比特，直接减小公式里的 `bytes(dtype)`。收益是显存占用和带宽下降，代价是精度损失、反量化开销和实现复杂度。它同样不替代管理机制。

## 7.4 收益与验证

| 手段 | 收益 | 代价 | 验证 |
|---|---|---|---|
| MLA | 每词元状态更小 | 实现复杂、可能损失表达 | TTFT、吞吐、质量 |
| KV 量化 | 显存/带宽下降 | 精度损失、反量化开销 | 输出质量、延迟、吞吐 |
| GQA/MQA | KV 头数减少 | 表达能力可能下降 | 质量与性能 |

这些是表示层的容量扩展，和分页、生命周期、前缀匹配是组合关系，不是替代关系。验证时同样要看 TTFT、吞吐、尾延迟和输出质量。

# 最后：一份速查表

| 概念 | 一句话记住 |
|---|---|
| KV Cache | 历史 K/V 的缓存，避免 Decode 重算历史 |
| MHA/GQA/MQA | KV 头数从多到少：$H$、中间、1 |
| MLA | 用低维潜在向量改变 KV 表示 |
| 容量公式 | $2 \times L \times H_{kv} \times D \times S \times B \times \text{bytes}$，近似线性增长 |
| PagedAttention | 固定块 + 块表，逻辑连续、物理离散 |
| 内部/外部碎片 | 预留过多 / 释放块零散难复用 |
| 引用计数 | 共享时加 1，归零才可回收；>0 绝不能驱逐 |
| reusable | 引用归零但暂留的缓存，仍算 allocated，不等于 free |
| 容量账本 | 真正约束是新请求的是 **free_blocks** |
| 驱逐顺序 | 先空闲池，再 `ref_count=0` 冷缓存，最后抢占/排队/拒绝 |
| 换出 vs 重算 | 换出省计算有传输；重算省传输浪费计算、增 TTFT |
| 前缀匹配 | 从开头连续逐 token 一致才算命中，中间相同不算 |
| 拆分不变量 | 可复用前缀 + 未命中后缀 = 原 prompt |
| 复用比例 | 命中词元数 ÷ 输入总词元数；空输入为 0 |
| Radix 树 | 压缩边前缀树，`terminal` 是完整缓存闸门 |
| 分裂不变量 | 旧后缀必须继承旧 children、terminal、kv_cache_ptr |
| 匹配停止 | 边中间分叉立即停止；只有 terminal 才更新命中长度 |
| 真实验证 | 命中率不等于收益，看 TTFT、吞吐、尾延迟、正确性 |
| MLA/量化 | 减少每词元字节，不替代分页/生命周期/前缀复用 |
