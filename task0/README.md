# 请求、工作负载与指标

这篇按六个部分展开：仅解码器生成路径、请求事件与状态、阶段指标、工作负载契约、失败与证据、真实后端基线验证。写法上先给定义，再给公式或数据，最后说明它在实际系统里对应什么。

---

## 一、仅解码器生成路径

### 1.1 什么是“仅解码器”（Decoder-only）模型

仅解码器（decoder-only）是当前主流大模型采用的架构，GPT 系列、LLaMA、Qwen、DeepSeek 都属于这一类。它没有单独的编码器，靠因果注意力（causal attention）保证每个位置只能看到自己及之前的 token，看不到后面的内容。训练目标是自回归语言建模：给定前 $t-1$ 个 token，预测第 $t$ 个。

这个结构决定了推理只能串行进行。第 1 个 token 没出来，第 2 个就无从计算。后面所有关于延迟和吞吐量的讨论，前提都是这一点。

### 1.2 自回归生成：一个词一个词地“蹦”

模型的输出不是一次写完的。每一步只产生一个 token，把它追加到输入末尾，再用新的序列预测下一个 token。

形式化一点：第 $t$ 步接收序列 $x_1, \dots, x_{t-1}$，输出概率分布 $P(x_t \mid x_1, \dots, x_{t-1})$，采样得到 $x_t$ 后追加进序列，进入第 $t+1$ 步，直到生成结束符（EOS token）或达到最大长度。

decode 阶段受限于显存带宽而不是算力，原因就在这里：每一步的计算量很小，但要把之前积累的状态反复读出来。

### 1.3 两个性质完全不同的阶段：预填充与解码

整条生成路径上最重要的一次划分，是把推理拆成 prefill 和 decode 两个阶段。

#### 预填充阶段（Prefill）：模型“一口气读完输入”

prefill 阶段对输入序列的所有位置并行做前向计算，算出每一层的 Key 和 Value 写进 KV Cache，最后得到第一个输出 token 的概率分布。注意力那部分的计算量随输入长度 $L$ 平方增长，所以这个阶段是计算密集型（compute-bound）。

prefill 的耗时直接落在 TTFT（首 token 延迟）里。输入越长，这部分越慢。

#### 解码阶段（Decode）：模型“一个字一个字地写答案”

decode 阶段每一步只处理一个新 token。它读取 prefill 和前面各步累积的 KV Cache，算出当前步的注意力输出，生成下一个 token，并把新的 Key/Value 追加进 KV Cache。每步计算量不大，但要读的 KV Cache 随序列长度线性增长，所以属于访存密集型（memory-bound），速度受显存带宽限制。

解码每步的耗时决定 TPOT（每输出 token 时间）。它慢不是算不动，是读不动。

#### 两个阶段的对比总结

| 维度 | 预填充 | 解码 |
|---|---|---|
| 每步处理词元数 | 全部输入词元（并行） | 1个新词元 |
| 计算特征 | 计算密集型 | 访存密集型 |
| 瓶颈 | 算力（FLOPs） | 显存带宽 |
| 对指标的影响 | TTFT | TPOT |
| KV Cache 操作 | 写入 | 读取 + 追加 |

### 1.4 KV Cache：贯穿两个阶段的“持久记忆”

KV Cache 存的是每一层注意力里已经算过的 Key 矩阵和 Value 矩阵。自回归生成中，第 $t$ 步的注意力要用到第 $1$ 到 $t$ 步的全部 Key 和 Value。不缓存的话每一步都要重算，总计算量是 $O(L^2)$；缓存之后，每步只算新 token 的 Key/Value 并追加，总计算量降到 $O(L)$。

这里有个容易搞错的地方，文章 A 特别强调过：KV Cache 不是一个独立阶段，而是一种贯穿始终的持久状态。prefill 写入它，decode 读取并追加它。它的大小随并发请求数、序列长度、层数、头数、维度增长，是推理显存占用中的主要变量。

所以 KV Cache 的大小直接决定峰值显存，也就决定了系统能同时服务多少用户。后面的 MHA/GQA/MLA 和 PagedAttention，处理的都是这份状态的体积和存放方式。

## 二、请求事件与状态

### 2.1 为什么要把请求建模成“事件序列”

一个请求不是一瞬间完成的事。它要经过若干环节：先排队等系统接收，再做输入预处理，然后 prefill，然后 decode，最后完成、取消、超时或者失败。每个环节的进出都打一个时间戳，才能知道时间具体花在哪里。

文章 B 的做法是把请求建模成事件驱动的状态轨迹：每个事件（event）携带时间戳，触发状态（state）切换，事件按时间单调排列，形成一条不可回退的轨迹。

如果只看端到端延迟一个数字，只能知道慢，不能知道是排队慢、预处理慢、prefill 慢还是 decode 慢。事件模型的作用就是做阶段分解，把瓶颈定位到具体环节。

### 2.2 状态机：请求经过哪些状态

文章 B 定义的状态序列如下：

```
未到达 → 排队 → 输入准备 → 预填充 → 解码 → 终止状态
```

逐个说明：

- **未到达（Not Arrived）**：请求还没进入系统，是初始状态。
- **排队（Queued）**：请求已到达，但还没被调度器接纳，停在等待队列里等 GPU 资源。进入这个状态的事件是到达（Arrival）。
- **输入准备（Input Preparation）**：请求被接纳（Admitted）后做输入预处理，比如分词（tokenization）、组装 prompt 模板。进入这个状态的事件是准入（Admission）。
- **预填充（Prefill）**：输入准备好后，模型一次性处理所有输入 token，写入 KV Cache，产出第一个输出 token。进入这个状态的事件是输入就绪（Input Ready）。
- **解码（Decode）**：第一个 token 产出后进入逐 token 生成。进入这个状态的事件是首个 token（First Token）。
- **终止状态（Terminal States）**：请求结束，有四种方式：
  - **已完成（Completed）**：正常生成到 EOS 或最大长度。
  - **已取消（Cancelled）**：客户端主动取消。
  - **已超时（Timed Out）**：超过系统设定的时间上限。
  - **已失败（Failed）**：发生错误，比如 OOM、后端异常。

这个状态机是后面所有指标计算的坐标系。TTFT 是“到达”到“首个 token”的时间差，TPOT 是 decode 状态内部相邻 token 的时间差。

### 2.3 两条硬规则：时间单调与终止不可逆

文章 B 明确了两条约束：

1. **时间必须单调**：后发生的事件，时间戳必须 **≥** 前一个事件的时间戳。不能出现“decode 事件比 prefill 事件还早”这种逻辑错误。
2. **终止后不能追加事件**：一旦请求进入已完成、已取消、已超时、已失败中的任一终止状态，就不能再有新事件追加进来。

这两条规则保证了事件轨迹的可信度。数据如果违反它们，说明采集或记录出了问题，基于它算出来的指标也不可信。这一部分在后面第五部分还会用到。

### 2.4 事件模型与连续批处理的关联

真实系统里，排队和准入不是一次性发生的，因为 GPU 是边干活边换人的。一个短请求生成完了，它的槽位立刻空出来，调度器马上从队列里拉一个新请求填进去。所以“排队 → 准入”这对事件会在运行中频繁、动态地出现。

连续批处理（continuous batching）在每一个 decode 步都检查是否有请求完成，完成后立即移出，空出的槽位从等待队列补入新请求。静态批处理（static batching）不是这样：一批请求绑在一起，必须等最慢的那个完成才能开始下一批，短请求做完后槽位会长时间空着。

连续批处理是提升吞吐量的关键机制，文章 A 给出的数字是静态批处理的 2 到 10 倍。它也把“排队”和“准入”变成请求生命周期里真实且频繁的事件，而不是一次性的前置步骤。

## 三、阶段指标

有了事件时间戳，指标计算就变成看两个事件之间的时间差。文章 A 和文章 B 共同定义了下面这套指标。

### 3.1 TTFT（Time to First Token，首词元延迟）

从请求发出到第一个 token 出现在屏幕上，这段时间就是 TTFT，它决定用户感觉模型反应快不快。

定义式：

```
TTFT = 首个词元事件的时间戳 − 到达事件的时间戳
```

它覆盖三个子阶段，这是文章 B 的重点：

| 子阶段 | 事件区间 | 说明 |
|---|---|---|
| 排队时间 | 到达 → 准入 | 在队列里等系统接收 |
| 输入准备时间 | 准入 → 输入就绪 | 分词、模板组装等预处理 |
| 预填充时间 | 输入就绪 → 首个词元 | 模型一次性读完所有输入并算出第一个词 |

TTFT 长不一定是模型算得慢。可能是在排队（系统繁忙），可能是输入预处理耗时（输入特别长或者格式复杂），也可能是 prefill 本身计算量大（输入长度大）。文章 B 强调做阶段分解，就是为了避免把“排队变慢”误判成“模型计算变慢”。

### 3.2 TPOT（Time Per Output Token，每输出词元时间）

第一个 token 出来之后，后续每个 token 平均隔多久出来一个，这个量决定模型的“语速”。

TPOT 衡量 decode 阶段内部相邻两个输出 token 之间的平均时间间隔，算法是 decode 阶段总耗时除以（输出 token 数 − 1）。

文章 B 特别强调了样本选择规则：TPOT 至少需要两个输出 token 才能算，因为要凑出一对相邻间隔。如果一个请求只产出一个 token 就结束了，它的 TPOT 应该标记为空（Null），不能用 0 填充。

用 0 填充会人为拉低平均 TPOT，制造“速度很快”的假象。这是“缺失证据不能用零值代替”原则的一个具体体现，见第五部分。

### 3.3 端到端延迟（End-to-End Latency）

从请求发出到最后一个 token 出来，总共等了多久，这就是端到端延迟。

定义式：

```
端到端延迟 = 终止事件的时间戳 − 到达事件的时间戳
```

它覆盖整个生命周期。和 TTFT、TPOT 的关系可以粗略写成：

> **端到端延迟 ≈ TTFT + (TPOT × 后续生成的词元数)**

也就是说，总时间由“首字等待”和“后续语速”两部分构成，优化其中任何一个都能改善总延迟。

### 3.4 吞吐量（Throughput）

吞吐量衡量单位时间内系统能服务多少请求、或者生成多少 token，看的是产能，不是单个请求的速度。

有两种常用度量：

- **请求吞吐量**：每秒完成的请求数（requests/s）。
- **词元吞吐量**：每秒生成的 token 数（tokens/s）。

离线批量处理任务（比如批量翻译一批文档）追求的是高吞吐量，用有限资源处理尽可能多的请求。吞吐量和延迟通常是权衡关系：把批处理规模做大能提高吞吐量，但可能拉长单个请求的排队时间和延迟。

### 3.5 延迟分位数：P50、P95、P99

分位数衡量的是稳定性，不是平均水平。

- **P50（中位数）**：50% 的请求在这个时间内完成，代表典型体验。
- **P95**：95% 的请求在这个时间内完成，剩下 5% 的慢请求决定用户会不会觉得卡。
- **P99**：99% 的请求都能在此时间内完成，是对最慢那 1% 请求的保障。

只看平均值不行，因为平均值会被少数极快的请求拉低，把让用户抓狂的慢请求掩盖掉。P95/P99 高企才是体验变差的直接信号。文章 A 明确指出，延迟分位数回答的是稳定性问题，不能和平均值互相替代。

### 3.6 峰值显存（Peak Memory）

峰值显存是服务过程中 GPU 显存占用最高时的数值。显存是有限资源，峰值决定了最多能同时服务多少用户，也就是并发规模。

主要构成有三块：

- **模型权重**：固定成本，由参数量和精度决定。
- **KV Cache**：随并发请求数和序列长度增长，是主要变量。
- **激活值**：中间计算结果，通常较小但不可忽略。

峰值显存直接决定并发上限。显存不够时，要么拒绝新请求（排队变长），要么触发 OOM（请求失败）。文章 A 强调，峰值显存回答的是“最多能同时服务多少人”，和 TTFT、TPOT、吞吐量回答的是完全不同的问题。

### 3.7 指标为什么不能互相替代（文章A的核心结论）

| 指标 | 回答的问题 |
|---|---|
| TTFT | 用户要等多久才看到第一个字？ |
| TPOT | 字蹦出来的速度有多快？ |
| 吞吐量 | 系统整体产能有多大？ |
| 峰值显存 | 最多能同时服务多少人？ |
| P95/P99 | 最慢的那部分请求有多慢？ |

一个系统可能 TTFT 很短但 TPOT 很长，也可能吞吐量很高但峰值显存同样高得吓人。这几个维度之间没有换算关系，只能同时看，才能对性能做准确判断。

## 四、工作负载契约

### 4.1 什么是“工作负载契约”

同一套指标，在不同测试条件下测出来的数值没有可比性。工作负载契约就是把这些条件明确记下来：输入多长、输出多长、多少并发、什么模型配置。没有它，指标数字没有意义。

工作负载契约（workload contract）是对推理负载特征的完整描述，包括：

- **输入长度分布**：prompt 的 token 数分布（平均值、P95、最大值）。
- **输出长度分布**：生成 token 数的分布。
- **并发数**：同时活跃的请求数。
- **请求到达模式**：均匀到达、突发到达还是持续满载。
- **模型配置**：架构类型、参数量、精度、注意力变体等。

文章 A 在讨论模型架构对推理成本的影响时明确指出，做性能测试必须记录模型的具体配置，否则同样的指标数值在不同配置下意义完全不同。

### 4.2 模型架构如何改变“工作量”

请求流程一样，模型的“体格”不同，执行成本也会差很多。文章 A 讲了两组架构差异。

#### 注意力变体：MHA、GQA、MLA——决定 KV Cache 的“体积”

- **MHA（多头注意力，multi-head attention）**：最经典的形态，每个查询头配一组独立的键值对。表达能力最强，KV Cache 也最大，推理时最占显存、最费带宽。
- **GQA（分组查询注意力，grouped-query attention）**：折中方案，把查询头分组，每组共享一组键值对。KV Cache 变小，在效率和表达能力之间取平衡。LLaMA 2/3 用的就是这个。
- **MLA（多头潜在注意力，multi-head latent attention）**：更激进的压缩方案，把键值对压成更小的潜在向量再存，KV Cache 能压得很小。DeepSeek 系列采用这类技术，目标是更快的推理。

一个粗糙的类比是记笔记：MHA 是每人记一份完整的，GQA 是几个人共享一份，MLA 是先把笔记压成摘要再共享。共享和压缩的程度越高，KV Cache 越小，表达能力可能打点折扣。

#### 稠密模型 vs. MoE——决定每次计算动用多少“脑细胞”

- **Dense（稠密模型）**：每生成一个 token，每一层的前馈网络全部参与计算，计算量大且固定。
- **MoE（混合专家模型，mixture of experts）**：模型里有很多专家网络，路由器根据当前 token 只挑少数几个（比如 2 个）激活。这样总参数量可以很大（知识容量大），但每次推理实际参与计算的激活参数很少，单次推理的计算成本因此大幅下降。

类比是考试：Dense 每次所有科目全考一遍，MoE 按题目类型只找相关科目的老师批改。总师资力量很大，每次动用的却很少。

### 4.3 为什么工作负载契约必须和指标一起报告

如果说“这个系统 TTFT 是 200ms”却不给输入长度、并发数和模型，这个数字毫无意义。输入 10 个 token 和输入 10000 个 token，TTFT 差得很远。

工作负载契约就是指标数值的上下文。同一个模型，短输入低并发下 TTFT 可能很低，长输入高并发下可能翻好几倍。所以任何性能报告都必须同时给出工作负载契约，否则指标不可复现、不可比较。

## 五、失败与证据

### 5.1 终止状态：请求不总是“完成”

文章 B 定义了四种终止状态：已完成、已取消、已超时、已失败。

不是每个请求都能正常走完。用户可能中途取消，系统可能超时，后端可能出错。这些非正常结束的请求不应该被静默丢弃，而要记成对应的终止状态。

如果把它们排除在统计之外，剩下的只有成功请求的指标，会造成幸存者偏差：系统看起来很快，实际上大量请求根本没成功。

### 5.2 缺失证据不能用零值代替

这是文章 B 反复强调的一条原则。

一个请求只生成了 1 个 token 就结束，它没有相邻 token 间隔，TPOT 应该是空，而不是 0。填 0 会让平均值好看，但那是假的。

更一般地说，某个指标在某个请求上无法计算时（比如 TPOT 需要至少两个输出 token），应标记为缺失（Null/NaN），聚合统计时明确排除，而不是用 0 填充。用 0 填充会系统性地低估指标值，制造性能假象。

这是数据可信度的底线。一个好看但虚假的指标比一个难看但真实的指标危害更大，因为它会把优化方向带偏。

### 5.3 时间单调性与终止不可逆：证据的完整性约束

文章 B 的两条硬规则（见 2.3）在这里有第二层含义：它们不只是建模约束，也是证据完整性的保障。

- **时间单调**：时间戳乱序说明采集系统有问题，基于它算出来的 TTFT/TPOT 不可信。
- **终止后不能追加事件**：终止后还有事件，说明状态机被破坏，这个请求的数据应标记为异常。

这相当于审计：账本上的日期是乱的，或者签收之后还有发货记录，这本账就不可信。

### 5.4 失败证据的用途：不是“扔掉”，而是“分类”

失败、取消、超时的请求不是垃圾数据，而是证据。它们能说明系统在什么条件下出问题：并发太高导致排队超时？输入太长导致 OOM？还是后端不稳定导致失败？

按终止状态分类统计，可以得到几个比率：

- **已完成率**：完成请求数 ÷ 总请求数，反映系统可靠性。
- **超时率**：超时请求数 ÷ 总请求数，反映排队或计算是否过慢。
- **失败率**：失败请求数 ÷ 总请求数，反映后端稳定性。

一个系统可能“成功请求的 TTFT 很低”，但超时率很高，说明大量请求根本没等到第一个字。只看成功请求的指标会严重高估系统表现。

## 六、真实后端基线验证

### 6.1 为什么需要“真实后端”验证

事件模型和指标公式是理论骨架，但真实系统里有很多理论没覆盖的细节，比如显存碎片、调度开销、批处理的动态变化。所以要在一个真实推理后端上跑一遍，看理论模型和实际行为对不对得上。

真实后端基线验证指的是：在真实的推理服务系统（vLLM、TensorRT-LLM、SGLang 这类）上，按工作负载契约施加负载，采集事件时间戳，计算指标，再和理论预期或基线系统对比。

理论模型容易漏掉真实系统的关键机制。下面两个机制必须纳入模型，并且要在真实后端上验证。

### 6.2 PagedAttention：解决 KV Cache 的“显存碎片”

传统做法是给每个请求预留一块连续的、足够大的显存来放 KV Cache。但请求的实际长度往往远小于预留上限，于是大量显存被浪费，还会产生碎片。

PagedAttention 借用了操作系统的虚拟内存分页思路：把 KV Cache 切成固定大小的页（page），这些页可以分散在不连续的物理显存里，用一张页表（page table）把逻辑位置映射到物理位置。这样显存就能按需分配，不需要整块连续空间。

文章 B 给出的效果是：显存有效利用率从传统方式的 20%–40% 提升到接近 100%，同样显存下可以服务更多请求，等于提高了峰值显存约束下的并发能力。

对指标的影响：PagedAttention 不改变 TTFT 或 TPOT 的计算公式，但它减少显存浪费，让同样显存能容纳更多并发，从而影响吞吐量和排队时间（进而影响 TTFT）。

### 6.3 连续批处理：让 GPU 在解码时“边干活边换人”

静态批处理像大巴，必须等所有乘客到齐才发车，到站后还要等所有人下车才能接下一批。连续批处理像地铁，每站都有人上有人下，车一直在跑。

连续批处理在每一个 decode 步检查是否有请求完成，完成后立即移出批处理，空出的槽位立即从等待队列补入新请求。GPU 很少因为等一个慢请求而闲置。

文章 A 给出的效果是：吞吐量可以达到静态批处理的 2 到 10 倍。

对指标的影响：连续批处理主要提升吞吐量，同时通过减少排队时间改善 TTFT。但它也可能增加单个请求的 TPOT，因为批处理中的请求数在动态变化，每一步的批大小不同。所以这里仍然要在吞吐量和延迟之间做取舍。

### 6.4 基线验证要验证什么

在真实后端上做基线验证，核心是检查下面几条和理论模型是否一致：

1. **事件轨迹是否符合状态机**：采集到的事件序列是否满足“未到达→排队→输入准备→预填充→解码→终止”的顺序，时间是否单调，终止后是否还有事件。
2. **TTFT 的阶段分解是否可复现**：排队、输入准备、预填充三个子阶段的耗时占比，是否与工作负载契约的预期一致（比如长输入时 prefill 占比应该更大）。
3. **TPOT 是否受显存带宽约束**：decode 阶段 TPOT 是否随 KV Cache 增大（序列变长、并发变多）而上升，符合访存密集型的预期。
4. **峰值显存是否与并发规模匹配**：PagedAttention 是否确实提升了显存利用率，使给定显存下能容纳的并发数符合预期。
5. **终止状态分布是否合理**：超时率、失败率是否在可接受范围内，失败请求是否被正确分类而不是被静默丢弃。

理论模型给出的是预期，真实后端验证给出的是实测。两者一致说明模型可信；不一致说明有隐藏机制需要补进模型，这正是基线验证的价值。

## 全篇总结：一条因果链

把六个部分串起来是一条完整的因果链：

> 仅解码器模型的自回归特性决定了生成必须分成 prefill 和 decode 两个性质不同的阶段。这两个阶段加上排队和预处理，构成一条事件驱动的状态轨迹。事件时间戳定义了 TTFT、TPOT、端到端延迟这些阶段指标。但这些数值只有在明确的工作负载契约（输入输出长度、并发、模型架构）下才有意义。采集数据时要遵守失败与证据的原则（终止状态分类、缺失不填零、时间单调）。最后在真实后端上验证理论模型，把 PagedAttention、连续批处理这些真实机制纳入进来，确认指标与系统行为一致。

理解了这条链，遇到一个变慢的推理请求时就能沿着事件轨迹往下问：它是在排队、在预处理、在 prefill 还是在 decode？在什么工作负载和模型配置下慢的？失败请求有没有算进去？真实系统的哪个机制导致了偏差？而不是只有一个模糊的“慢”的感觉。
