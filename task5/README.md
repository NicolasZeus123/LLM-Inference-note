# 低精度执行与单卡部署准入

这篇按六个环节，把 05_quantized_inference_and_deployment、52_Quantization_Calibration_and_Error、25_Quantization_W8A16、INF-EXECUTION-DISPATCH 四份内容串成一条链。每个环节先说这一步在干什么，再说涉及哪些概念，最后说它和下一步的接口在哪。

---

## 第一环：浮点基线——先搞清楚“不量化的时候，模型是怎么跑的”

### 1.1 模型里到底有哪些数字

一个训练好的 Transformer 模型，推理时涉及三类数字。

**权重（Weight）**：训练完固定下来的参数，存在模型文件里，推理时只读不改。

**激活值（Activation）**：输入数据经过每一层计算后产生的中间结果，随输入变化。比如第一层做完矩阵乘法得到的张量，就是下一层的激活值输入。

**KV Cache**：Transformer 是自回归生成的，生成第 t 个 token 需要前面所有 token 的信息。为了避免重复计算，模型把前面 token 的 Key 和 Value 缓存下来，这就是 KV Cache。它的大小与上下文长度和并发批量成正比。

### 1.2 默认的浮点格式

模型默认用 FP16（16 位浮点数）或 BF16（16 位脑浮点数）存储和计算，每个数字占 2 个字节。

FP16 和 BF16 都是 16 位，区别在于位数怎么分配：FP16 给尾数（精度）更多位，BF16 给指数（范围）更多位。对推理来说，两者都属于浮点基线。

FP32 是 32 位浮点数，精度更高但占用翻倍，推理时很少用。

### 1.3 浮点基线下的计算流程

一个线性层的前向计算是 FP16 激活值 × FP16 权重 → FP16 输出。矩阵乘法的两个操作数都是浮点数，走的是 FP16 GEMM（通用矩阵乘法），由 GPU 的浮点计算单元执行。

这个基线就是后面所有量化讨论的参照系。量化的每一个动作都在回答同一个问题：把基线里的哪个数字换成更低精度，换完之后省了什么、损失了什么、执行路径有没有变。

## 第二环：量化对象与误差——压什么、怎么压、压坏了什么

### 2.1 量化的定义

量化就是把高精度浮点数映射到低精度表示。FP16 每数字占 2 字节，INT8 占 1 字节，INT4 只占 0.5 字节。位数越少，占用越小，但能表示的数值范围和精度也越受限。

文章把量化定义为资源占用与表示误差之间的交换：换来更少的显存和带宽消耗，代价是接受一定的精度损失。

### 2.2 量化对象：三类，解决的问题完全不同

**权重量化（Weight Quantization）**：只压静态权重，不碰激活值。最直接的好处是模型文件变小、加载进显存后占用变少。如果问题是“模型根本装不进显卡”，权重量化是第一优先级。

**W8A16** 是最基础的权重量化路线。W 是 Weight，A 是 Activation，W8 表示权重压到 8 位，A16 表示激活值保持 16 位不动。它的精度损失很小，因为激活值完全没被量化；但速度提升有限，因为计算仍然是 FP16 的浮点矩阵乘法，没有用上 INT8 整数计算单元的加速能力。W8A16 的收益来自权重读取量减半，而不是算得更快。

**权重与激活量化（Weight + Activation Quantization）**：W8A8 表示权重和激活值都压到 8 位。潜在收益更大，不仅省显存，还可能让计算本身也变快，因为矩阵乘法可以在 INT8 下完成。但难度更高：激活值的分布随输入变化，容易出现离群值（少数特别大的数），直接量化会把整体精度拉垮。SmoothQuant 这类方法专门处理激活离群值问题。

**FP8** 是 8 位浮点数，动态范围比 INT8 大，能更好地容纳离群值，但尾数精度更少。FP8 能不能真正加速高度依赖硬件：较新的 GPU 有 FP8 计算单元，老硬件上可能只能存不能算。

**KV Cache 量化**：把缓存里的 Key/Value 用更低精度存储，在长上下文或高并发时省出缓存预算。Key 和 Value 的分布特性不同，可能需要不同的量化轴，而且要小心离群点。

### 2.3 量化的数学：量化网格、缩放因子、整数码

以对称 INT8 量化为例，核心公式只有三个：

> `scale = range / qmax`
> `q = clamp(round(x / scale), -qmax, qmax)`
> `x_hat = q × scale`

`x` 是原始浮点数。`q` 是量化后的整数码，INT8 对称量化下范围是 `[-127, 127]`，即 `qmax = 127`。`scale` 表示每个整数码代表多大的浮点值。`x_hat` 是解码恢复出来的近似值。

可以把量化想成一把只有 255 个刻度的尺子（从 -127 到 +127），`scale` 是每一格代表多少。量化网格就是尺子上的刻度线：`scale` 越小网格越密，`scale` 越大网格越稀。整数码就是浮点数落到了第几格。

为什么用 127 而不是 128？因为这是对称量化，正负两侧共用同一个缩放因子，整数码范围必须对称。牺牲一个负刻度换取整个映射的简洁对称，是常见的设计取舍。

**反量化（Dequantization）**：量化后的 INT8 权重不能直接和 FP16 激活值做矩阵乘法，数据类型不匹配。计算前要把 INT8 权重恢复成 FP16，公式是 `x_hat = q / scale`。注意 `x_hat` 已经不是原始值，它和原始值之间隔着舍入误差。

### 2.4 两种误差：舍入误差 vs. 裁剪误差

这是理解量化校准的核心矛盾。

**舍入误差（Rounding Error）**：浮点数无法精确落在整数刻度上，只能四舍五入到最近的刻度。范围越大（尺子越粗），舍入误差越大。尺子每格 0.1，`1.73` 只能落到 `1.7`，误差 `0.03`。

**裁剪误差（Clipping Error）**：数值超出设定的量化范围时被强行压到边界上，信息丢失。范围越小（尺子越短），裁剪误差越大。范围定在 `[-2, 2]`，来了一个 `100`，被压成 `2`，误差 `98`。

**饱和率（Saturation Rate）**：被压到边界之外的数值占总数的比例。饱和率越高，裁掉的信息越多。

校准的核心任务就是在这两者之间取折中：网格太粗导致舍入误差大，范围太窄导致饱和率高，要挑一个都能接受的点。

### 2.5 怎么选范围：分位数与校准集/验证集隔离

**分位数（Quantile）**：把一组数据从小到大排列，第 p 分位数就是有 p 比例的数据小于等于这个值。量化校准里对绝对值取分位数。`clipping_quantile = 0.9` 的意思是取所有绝对值中第 90 百分位对应的数值作为范围边界，剩下 10% 更大的值会被裁掉。

分位数越低，范围越窄，网格越细，但饱和率越高。

**校准集（Calibration Set）** 用来生成候选范围，即算分位数、算 `scale`。**验证集（Validation Set）** 用来评估候选好坏，绝对不能参与 `scale` 的计算。用同一批数据既定范围又测误差，测出来的误差是对被校准样本的记忆，不是对新数据的真实表现。

流程是固定的：用校准集对每个候选分位数算出 `scale` → 用这个固定的 `scale` 去量化验证集 → 在验证集上算 MSE（均方误差）和饱和率 → 先淘汰饱和率超标的候选 → 在剩下的里选 MSE 最低的 → 全都不达标就明确失败，而不是随便退回一个分位数。

### 2.6 两种常被比较的权重量化算法：GPTQ 和 AWQ

两者解决同一个问题：把权重压到 4 位或 8 位时，怎样让误差尽量小。

**GPTQ** 逐层逐列地量化权重，每量化一列，就用剩下未量化的权重去补偿已经引入的误差。它利用损失函数对权重的二阶信息（Hessian）判断哪些权重的误差影响更大、需要更小心处理。换句话说，不是所有数字都一样重要，GPTQ 尽量让重要的数字错得少一点。

**AWQ** 的角度不同：它认为权重的重要性不由权重本身的大小决定，而由它对应的激活值幅度决定。某个通道的激活值很大，该通道上的权重误差就会被放大传播，所以要重点保护这些显著权重。AWQ 通常只保护约 1% 的显著通道，就能大幅降低量化误差。

两者的共同点是：都在部署前用校准数据一次性生成量化权重，推理时不再需要校准。另外要记住，GPTQ 和 AWQ 是算法，不是文件格式。

## 第三环：产物——量化之后拿到了什么

### 3.1 产物的定义

推理部署产物是经过量化、转换或编译后交给加载器的文件。GPTQ 生成的量化权重、AWQ 生成的权重、GGUF 文件，都属于产物。

产物只证明格式上可以被加载，不证明运行时真的走了低精度路径。

### 3.2 GGUF：和 GPTQ / AWQ 不在同一个层面

这一点最容易被混淆。

GPTQ 和 AWQ 是“怎么算”的算法，GGUF 是“怎么存”的文件格式。GGUF 把量化后的权重、模型配置、分词器等信息打包进一个单文件，方便 llama.cpp 这类推理框架加载和执行。

GGUF 内部可以使用不同的量化方案，比如 K-quant 家族的 Q4_K_M、Q5_K_M，这些方案不是 GPTQ 也不是 AWQ，而是 llama.cpp 自己的一套量化策略。

所以不能把 GGUF 当成 GPTQ/AWQ 算法。用 GPTQ 算法产出的量化权重，和 GGUF 文件，是两个层面上的东西。

### 3.3 部署链的三层区分

部署链可以拆成三层：

**训练模型**：训练完保存下来的东西，包含架构、权重、分词器、可继续训练的配置，是源头。

**推理部署产物**：经过量化、转换或编译后交给加载器的文件。GPTQ 权重、AWQ 权重、GGUF 文件都属于这一层。

**推理引擎 / 运行时**：真正管事的，负责加载产物、管理 KV Cache、调度请求、调用计算内核。同一个产物在不同运行时上可能走完全不同的路径。

可以加载只证明格式兼容，不证明已经命中目标低精度路径。

## 第四环：加载器——谁把产物读进来

### 4.1 加载器的角色

加载器（loader）是推理引擎里负责读取产物文件、解析格式、把权重放进显存的组件。llama.cpp 能加载 GGUF 文件，vLLM 能加载 GPTQ/AWQ 权重，TensorRT-LLM 能加载它自己编译后的引擎文件。

加载器做的事情包括解析文件头、识别量化格式、分配显存、把 INT8/INT4 权重按格式要求摆放。加载成功只说明格式被识别了，不说明后续计算会走低精度路径。

### 4.2 加载器之后的下一步：执行后端

加载器把权重放进显存之后，真正决定怎么算的是执行后端，也就是下一环。

## 第五环：执行后端——谁来决定“这段计算交给谁执行”

### 5.1 后端的三种执行方式

**Eager（即时执行）**：逐算子执行，不做融合，最稳妥但最慢。PyTorch 默认模式就是 eager。

**编译后端（Compiled Backend）**：把计算图编译成优化后的执行计划，可能包含算子融合。比如 PyTorch 的 `torch.compile`、TensorRT-LLM 的图编译器。

**专用计算内核（Specialized Kernel）**：针对特定模式手写的高度优化内核，比如 FlashAttention、融合的 RMSNorm 内核、INT8 GEMM 内核。

### 5.2 后端分派（Backend Dispatch）

后端分派就是决定这段计算交给谁执行的过程。真实系统里通常通过算子注册表实现：每个算子在不同后端下可能有多个实现，调度器根据当前条件挑最合适的那个。

### 5.3 能力门槛（Capability Gate）

一个候选要通过执行后端的能力门槛，才能进入编译图或专用计算内核。门槛检查的维度包括：

**设备**：当前 GPU 架构是否支持该内核，比如 INT8 Tensor Core 需要较新的架构。

**执行后端**：当前加载的是哪个后端，比如 vLLM 的某个 kernel 后端、TensorRT-LLM、llama.cpp。

**计算内核约束**：dtype、shape、布局是否匹配。比如某个融合内核要求隐藏维度是 128 的倍数，或者要求权重已经是某种量化格式。

**寄存器压力**：融合后内核需要的寄存器数量是否超过硬件限制。

如果没有任何后端注册了能处理当前输入条件的实现，就必须回退（fallback）。

## 第六环：计算内核或回退——最终实际跑了什么

### 6.1 命中计算内核

能力门槛全部通过，计算就进入编译图或专用计算内核。这时应该能看到融合内核真的被执行、INT8 GEMM 真的被调用、权重读取真的减半。

### 6.2 回退（Fallback）

回退是后端分派的反面：优化路径不可用时，退回一个能正确执行但可能更慢的路径。

文章原文的说法是“否则必须回退，并记录失败原因”。回退不是静默失败，它需要留下执行证据（evidence），让人知道实际执行了什么、为什么没走优化路径。

回退本身不算错误，它保证了正确性。但如果以为自己跑的是融合内核，实际跑的是 eager，性能预期就会落空。

### 6.3 最容易被混淆的一点：“编译成功” ≠ “命中融合内核”

编译成功只说明图通过了编译流程，不说明最终执行的代码真的走了融合路径。一个模式被识别、被编译，后端仍可能在运行时因为实际输入条件拒绝它，退回普通路径。比如某个张量的 dtype 和编译时的假设不一致，或者 shape 落在回退区间。

所以必须用运行证据来区分：实际执行的内核名称、执行路径的 trace、或者 profiler 输出。只看“编译成功”的日志是不够的。

### 6.4 融合候选：哪些模式“值得被注意”

典型的 LLM 推理融合候选有四个，每一个都有对应的常见限制。这也是“候选不等于保证”的具体体现。

**QKV 投影 + RoPE（旋转位置编码）**：把线性投影和位置编码合并。限制在注意力头布局和位置编码实现上，如果 head 的排布方式或 RoPE 的实现方式和后端期望的不一致，后端可能拒绝这个融合。

**残差相加 + RMSNorm**：把残差连接和归一化合并。限制在数据类型、隐藏维度和数值稳定性。某些后端对 RMSNorm 的输入 dtype 有严格要求，或者隐藏维度不是特定值的倍数时，融合可能不被接受。

**线性映射 + SiLU + 逐元素乘法**：这是 SwiGLU 激活函数的中间段。限制在张量形状、寄存器压力和量化格式。如果权重已经是量化格式，后端可能没有对应的融合内核支持这种组合。

**Logits 处理 + 采样**：把最后的 logits 处理和采样策略合并，减少多次小内核启动。限制在动态策略和随机数状态上，采样涉及随机数生成，融合后随机数状态的管理会变复杂，后端可能因此拒绝。

这些模式被识别出来，只说明它们在语义层面可以融合。后端接不接受，取决于它有没有能力处理这个特定组合在特定输入条件下的情况。

### 6.5 部署时真正该看的指标

**TTFT（Time to First Token，首 token 延迟）**：请求发出后第一个 token 出来要等多久，主要受输入长度（prefill 阶段）和缓存命中情况影响。

**TPOT（Time Per Output Token，每输出 token 时间）**：第一个 token 出来之后，后面每个 token 平均间隔多久，反映 decode 阶段的持续生成速度。

**吞吐（Throughput）**：单位时间内能服务多少请求或生成多少 token。

**P99 延迟**：最慢那 1% 的请求有多慢，用来衡量尾延迟。平均值好看不代表体验好。

判断量化是否成功，不能只看峰值显存降了多少，而要把 TTFT、TPOT、吞吐、P99 和峰值显存放一起，在固定模型、固定输入输出长度、固定并发下做配对比较。显存降了但速度没变，说明计算内核没有受益；速度上去了但质量回归了，说明量化误差超出了可接受门槛。

### 6.6 质量验证要分层

量化可能让输出的数值看起来差不多，但会改变 decode 行为，比如更容易重复、更容易偏离格式、在长上下文里更容易忘记约束。所以质量验证要分层：

**数值层**：有没有非有限值，logits 差异是否异常。

**生成层**：固定 prompt 下，停止条件、输出长度、重复率有没有变化。

**任务层**：目标任务准确率、结构化格式、工具调用成功率是否仍然达标。

**服务层**：TTFT、TPOT、吞吐、P99、峰值显存是否真正改善。

只有产物对得上、内核命中、工作负载下指标改善、任务质量仍然可接受，量化才算在部署意义上成立。

## 整条链的总结

**浮点基线**说明不量化时模型怎么跑：FP16 权重 × FP16 激活值，走 FP16 GEMM。

**量化对象与误差**说明压什么、怎么压、压坏了什么：权重、激活、KV Cache 三类对象；量化网格越粗舍入误差越大，范围越窄裁剪误差越大；校准要在两者之间取折中，校准集和验证集必须隔离。

**产物**说明量化之后手里拿到了什么：GPTQ/AWQ 权重、GGUF 文件。产物只证明格式兼容，不证明执行路径。

**加载器**把产物读进来，放进显存。

**执行后端**通过能力门槛决定这段计算交给谁执行：eager、编译图、专用内核。门槛检查设备、后端、dtype、shape、寄存器压力。

**计算内核或回退**是最终结果：命中融合内核或低精度内核，或者回退到普通路径并记录原因。编译成功不等于命中融合内核，必须用运行证据区分。最后用 TTFT、TPOT、吞吐、P99 和分层质量验证判断量化是否真的在部署意义上成立。

整条链的立场是：量化不是把位数调低这一个动作，而是从浮点基线出发，经过对象选择、误差校准、产物生成、加载、后端分派，最终落到实际计算内核或回退的完整链路。每一环都有“看起来成了”和“实际成了”的区别，只有运行证据和配对指标才能确认收益真正落地。
