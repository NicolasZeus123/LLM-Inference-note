# 注意力计算与执行分派

这篇把三部分内容（MHA/GQA、FlashAttention、inference fusion 与 backend dispatch）串成一条线，用一个固定的 Task0 工作负载作为算例，从“要算什么”一路走到“怎么高效算出来”。

---

## 第 1 站：复用 Task0 工作负载 —— 先确定“要算什么”

### 1.1 什么是“工作负载（Workload）”

工作负载就是一次推理任务的具体配置清单：处理多少条序列、用什么精度、序列多长、模型有多少个头。没有这组参数，后面所有“省了多少”都没法算。

### 1.2 Task0 是什么

Task0 是贯穿全文的一个固定算例，参数如下：

| 参数 | 符号 | 值 | 含义 |
| :--- | :--- | :--- | :--- |
| 批大小 | `B` | 2 | 一次处理 2 条序列 |
| 序列长度 | `N` | 1024 | 每条序列 1024 个 token |
| 查询头数 | `H` | 32 | 注意力有 32 个查询头 |
| KV 头数 | `H_kv` | 8 | 只有 8 个 KV 头（GQA 分组） |
| 每个头的维度 | `d` | 128 | 每个头的向量长度 |
| 数据类型 | `dtype` | FP16 | 半精度浮点，2 字节/元素 |
| 设备 | `device` | CUDA | 在 GPU 上执行 |

先定 Task0 的原因很简单：头表示、KV 建立、分块、后端选择这几步都要代入具体数字，才能看出省了多少、为什么这样选。

### 1.3 “复用”是什么意思

复用指的是同一份 Task0 配置贯穿多个阶段和多个优化决策。prefill 用它，decode 也用它；FlashAttention 的分块用它，后端分派的能力检查还用它。这样才能看到同一个工作负载在不同环节会撞上什么约束、触发什么优化。

## 第 2 站：注意力头表示 —— 搞清楚 Q/K/V 到底有几个头

### 2.1 回顾：Q、K、V 是什么

注意力里每个 token 会生成三个向量：

- **Q（Query，查询）**：当前 token 想找什么
- **K（Key，键）**：每个 token 的标识，用来和 Q 匹配
- **V（Value，值）**：每个 token 的内容，匹配后按权重聚合

所谓“头（head）”，就是把这些向量切成多份，每份独立做一次注意力，最后拼起来。相当于同一个问题派若干组人分别查资料，再汇总。

### 2.2 三种头表示方式

设查询头数为 `H = 32`，KV 头数为 `H_kv`：

| 方式 | `H_kv` | 含义 | Task0 中 |
| :--- | :--- | :--- | :--- |
| **MHA**（多头注意力） | `H_kv = H = 32` | 每个查询头都有自己独立的 K/V 头 | 不采用 |
| **MQA**（多查询注意力） | `H_kv = 1` | 所有查询头共享同一组 K/V | 不采用 |
| **GQA**（分组查询注意力） | `1 < H_kv < H` | 查询头分组，每组共享一组 K/V | **采用：H_kv=8** |

### 2.3 Task0 的 GQA 具体分组

`H = 32` 个查询头，`H_kv = 8` 个 KV 头，意味着：

- 每组有 `H / H_kv = 32 / 8 = 4` 个查询头
- 第 0~3 号查询头共享第 0 号 KV 头
- 第 4~7 号查询头共享第 1 号 KV 头
- 依此类推，共 8 组

4 个查询头看同一组 K/V，比 MHA 的每人一份省，比 MQA 的 32 人共享一份多一点表达能力。这里是表达能力和效率之间的取舍。

### 2.4 为什么头表示会影响后面所有步骤

- KV Cache 的大小直接由 `H_kv` 决定，第 3 站会算具体数字
- FlashAttention 的分块按头组织，第 4 站讲
- 后端能力检查要看 `H_kv` 是否在后端支持范围内，第 5 站讲

所以头表示要先定，后面才有具体数字可算。

## 第 3 站：预填充建立 KV —— Prefill 阶段把“底稿”存好

### 3.1 什么是预填充（Prefill）

大模型生成文本分两个阶段：

1. **预填充（Prefill）**：一次性处理用户输入的整个 prompt（Task0 中 `N=1024` 个 token），把所有 token 的 K 和 V 算出来存进 KV Cache。这一步是并行的，1024 个位置一次算完。
2. **解码（Decode）**：逐 token 生成。每生成一个新 token，只算这个新 token 的 Q，再和 KV Cache 里已有的 K/V 做注意力。

prefill 的任务就是建立 KV 状态，为 decode 准备好底稿。

### 3.2 KV Cache 到底存了什么、有多大

KV Cache 存的是每个 KV 头、每个位置的 K 向量和 V 向量。Task0 下的显存占用：

```
KV Cache 大小 = 2（K和V） × B × H_kv × N × d × sizeof(dtype)
             = 2 × 2 × 8 × 1024 × 128 × 2 字节
             = 8,388,608 字节 ≈ 8 MB
```

对比一下：如果换成 MHA（`H_kv = 32`），同样配置下 KV Cache 是 `2 × 2 × 32 × 1024 × 128 × 2 ≈ 32 MB`，正好是 GQA 的 4 倍。头表示对显存的影响在这里具体体现出来。

### 3.3 预填充阶段的计算特点

- 计算密集：1024 个位置并行做注意力，`N × N` 的分数矩阵很大
- 需要 FlashAttention：标准注意力在这里会撞上第 4 站要讲的 N² 搬运问题
- 产出：完整的 KV Cache（8 MB）加上最后一个位置的输出，用于开始解码

## 第 4 站：分块工作集与融合 —— 让预填充在“办公桌”上高效完成

FlashAttention 的分块（tiling）和编译层面的算子融合（fusion）放在一起讲，是因为它们处理同一个问题的两个层面：减少慢速内存访问和内核启动开销。

### 4.1 先弄懂 GPU 的“办公桌与档案库”

- **HBM（高带宽显存）**：容量大（几十 GB），带宽约 2 TB/s，搬数据慢
- **SRAM（片上共享内存）**：容量小（每计算单元约 164 KB），带宽约 19 TB/s，是 HBM 的 10 倍

计算核心只能在 SRAM 上工作，数据必须先搬过来。瓶颈在搬，不在算。

### 4.2 标准注意力的“N² 搬运灾难”

标准注意力要创建 `N × N` 的分数矩阵。Task0 中 `N=1024`，`N² ≈ 100 万`个元素，每个头一份，8 个 KV 头、2 个 batch 乘上去数量更大。这个矩阵反复写进 HBM 再读回 SRAM，大部分时间花在搬运上，属于内存带宽受限（memory-bound）。

### 4.3 分块（Tiling）：把大矩阵切成“能放上办公桌”的小块

分块就是把 Q、K、V 切成能完全塞进 SRAM 的小块，流程是：

1. 从 HBM 加载一小块 Q 和一小块 K、V 到 SRAM
2. 在 SRAM 内就地完成矩阵乘、Softmax、乘 V
3. 只把最终输出块写回 HBM
4. 换下一块重复

关键在于那个 `N × N` 的中间矩阵从来没有被完整创建、也没有写进 HBM。搬运量从 `O(N²)` 降到 `O(N)` 级别。

### 4.4 在线 Softmax：分块下的数学难题与解法

Softmax 需要一整行的全局最大值和指数和才能归一化，而分块处理时，算到最后一块之前拿不到全局信息。

在线 Softmax 维护两个逐行状态：`m`（已见最大值）和 `ℓ`（已见指数和）。每来一个新块：

1. 算局部最大值和局部指数和
2. 与累积状态合并；如果新最大值更大，更新 `m` 并重新缩放（rescaling）之前累积的输出
3. 更新 `ℓ`

这样最终结果和一次性看整行完全一致，数学上精确等价。

### 4.5 算子融合（Fusion）：把多个小步骤合成一个大步骤

算子（operator）是计算图里的一个基本运算，比如矩阵乘、加法、SiLU 激活。eager 模式下每个算子单独启动一次内核，数据反复读写 HBM。

算子融合把有依赖关系的多个细粒度算子合成一个融合内核，数据读入一次、在芯片内完成多步计算、写出一次。典型的融合模式：

| 融合模式 | 融合了什么 | 收益 |
| :--- | :--- | :--- |
| **QKV 投影 + RoPE** | 生成 Q/K/V 的线性投影与旋转位置编码 | 减少中间张量写回和内核启动 |
| **残差相加 + RMSNorm** | 残差连接加法与归一化 | 减少重复读写 |
| **线性映射 + SiLU + 逐元素乘** | SwiGLU 激活的标准三步 | 避免中间激活值落地 |
| **Logits 处理 + 采样** | 输出层温度缩放与 Top-K 采样 | 减少多次小内核启动 |

### 4.6 分块与融合的关系

- 分块解决的是“大矩阵不要落地 HBM”，属于 FlashAttention 层面
- 融合解决的是“多个小算子不要反复启动和读写”，属于编译优化层面

两者叠加之后，prefill 阶段的计算工作集被控制在 SRAM 能容纳的范围内，HBM 搬运和内核启动都明显减少。

## 第 5 站：执行后端能力门槛 —— 优化不是想用就能用

### 5.1 什么是“后端（Backend）”

后端是执行计算的具体引擎或路径：

- **Eager**：PyTorch 默认的即时执行，最基础也最灵活，但性能有损失
- **编译后端**：如 `torch.compile` 的 Inductor，生成融合后的高效代码
- **专用库/内核**：如 FlashAttention、FlashInfer、cuDNN，为特定操作提供高度优化的实现

### 5.2 什么是“后端分派（Backend Dispatch）”

分派就是为当前计算任务，从可用后端里挑一个最合适的来执行。这里要分清一点：后端装了，不等于当前这个候选能跑。

### 5.3 能力门槛（Capability Gates）

分派器依次检查下面几项，任何一项不满足就换下一个后端：

| 门槛 | 检查什么 | Task0 中的例子 | 不满足的后果 |
| :--- | :--- | :--- | :--- |
| **模式（Pattern）** | 后端是否声明支持这个融合模式 | FlashAttention 是否支持“QKV+RoPE”融合 | 换后端 |
| **数据类型（dtype）** | 内核是否支持当前精度 | 某内核只支持 FP16/BF16，Task0 是 FP16 ✓ | 换精度或回退 |
| **设备（Device）** | 是否支持当前硬件 | Task0 是 CUDA ✓；若是 CPU 则可能不支持 | 换路径或回退 |
| **形状（Shape）** | 序列长度等是否在支持上限内 | 某内核最大支持 `N=2048`，Task0 的 `N=1024` ✓ | 重新编译、分桶或回退 |
| **动态形状（Dynamic Shape）** | 输入形状动态时能否处理 | Task0 形状固定 ✓ | 固定形状、分图或 Eager 回退 |

### 5.4 回退（Fallback）机制

如果所有优化后端都至少有一项门槛不满足，系统必须回退到 eager 模式执行，保证正确性优先，同时把拒绝原因记录下来方便排查。

Task0 的形状固定（`B=2, N=1024`）、FP16、CUDA，大概率能命中 FlashAttention 和融合路径；换成动态形状或 FP32 就可能触发回退。

## 第 6 站：向解码阶段交付 KV 状态 —— 把底稿交给下一棒

### 6.1 交付的是什么

prefill 完成后，交给 decode 的核心产物有两样：

1. **完整的 KV Cache**：Task0 下约 8 MB（`2 × B × H_kv × N × d × 2 字节`），包含 8 个 KV 头、1024 个位置的 K 和 V
2. **最后一个位置的输出隐藏状态**：用来生成第一个新 token

### 6.2 解码阶段怎么用这份 KV 状态

decode 是逐 token 进行的。每生成一个新 token：

1. 只算这个新 token 的 Q（1 个位置，不是 1024 个）
2. 用这个 Q 和 KV Cache 里所有已缓存的 K/V 做注意力
3. 把新 token 的 K/V 追加到 KV Cache
4. 输出下一个 token

prefill 是“一次算 1024 个位置”，decode 是“每次算 1 个位置”。所以 prefill 计算密集，需要分块优化；decode 内存带宽密集，需要频繁读写 KV Cache。

### 6.3 GQA 在解码阶段的红利

decode 每一步都要读 KV Cache。Task0 的 GQA（`H_kv=8`）相比 MHA（`H_kv=32`），KV Cache 小 4 倍，每步要读的数据也少 4 倍，解码速度因此明显提升。第 2 站的头表示选择，收益在这里兑现。

### 6.4 完整链路回顾

```
Task0 工作负载（B=2, N=1024, H=32, H_kv=8, d=128, FP16, CUDA）
        │
        ▼
注意力头表示：GQA，32 个查询头分 8 组，每组 4 头共享 1 组 KV
        │
        ▼
预填充建立 KV：并行算 1024 个位置，产出约 8 MB KV Cache
        │
        ▼
分块工作集与融合：FlashAttention Tiling + 在线 Softmax + 算子融合
        │   （在 SRAM 内完成，避免 N² 矩阵落地 HBM）
        ▼
执行后端能力门槛：模式/dtype/设备/形状/动态形状逐项检查
        │   （命中优化路径则用 FlashAttention + 融合；否则回退 Eager）
        ▼
向解码阶段交付：8 MB KV Cache + 最后位置输出
        │
        ▼
解码阶段：逐 token 生成，每步读 KV Cache（GQA 使其小 4 倍）
```

### 6.5 一句话总结

Task0 定义了要算什么；头表示决定了 KV 有几个头；prefill 把 KV 算出来存好；分块和融合让 prefill 在 SRAM 里高效完成；后端能力门槛决定走哪条执行路径；最后把 KV 状态交给 decode 逐 token 使用。整条链路的原则是：在保证正确性的前提下尽量利用硬件层次和软件优化，但任何门槛不满足就安全回退。
